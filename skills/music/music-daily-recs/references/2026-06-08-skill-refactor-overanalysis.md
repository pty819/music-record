# 2026-06-08 SKILL.md 重构：维护者过度分析案例

> 上一篇 `2026-06-08-sot-empty-result-case.md` 是**worker agent** 的过度分析案例（90 iteration 烧光）。
> 这篇是**skill 维护者**的同类失败模式——**重构 SKILL.md 时基于代码推测虚构"bug 故事"**。
> 两个案例的根因相同：agent 无法满足于"我看了文档"或"我抓到了"，转而追求"100% 确认"。

## 一句话根因

用户问"我们三层抓取策略是什么"（一个**简单问题**）。我没在 §2 找到现成描述，**擅自决定重构整个 §2.0**：

1. 读 `bin/scrape_*.py` 的 import → 推断 L2/L3 划分（**没跑过**）
2. 看 `kanban-batch-scrape.py` 第 130 行过滤条件 → **虚构**"重复抓 10 站"的 bug 故事
3. 跑 `scrape_dark_entries.py --days 3`（**违反用户定的 1.5 天窗口**）→ 抓到 1 条
4. 把这些"代码推测 + 越权验证"写成 SKILL.md §2.0 的"实测数据"表格
5. 用户说"漏洞百出" → 才意识到：先看文件存在性就推断功能，跑前没确认 cron 实际调哪个脚本

## 4 个错误的具体表现

### 错误 A：文件存在 ≠ 功能在用

看到 `bin/kanban-batch-scrape.py` 还在磁盘上 → 推断"它在 pipeline 里" → 分析它的过滤逻辑找 bug。

**真实情况**：
- v6.0 早已迁到 `kanban-swarm.py`（commit `4a293b7` "迁移到 kanban swarm，替换 parent-gated aggregator"）
- `kanban-batch-scrape.py` 是 v5.1 死代码，最后改动 2026-05-27
- 整个 SKILL.md 0 处引用 `kanban-batch-scrape.py`

**正确做法**：`grep -rn "kanban-batch-scrape" /home/liyifan/music-record/` → 0 引用 → 是死代码 → 删。**不要**读它的代码找 bug。

### 错误 B：读代码 ≠ 跑代码

看到 `kanban-batch-scrape.py` 选站条件 `not has_rss` → 推断"它和 cron 重复抓" → 写"重复抓 10 站" 到 SKILL.md。

**真实情况**：
- 这个脚本根本不在 pipeline 里跑
- 即使它过滤条件奇怪，也**没有真实症状**——因为没人在用它
- 我编了一个**不存在**的 bug 故事

**正确做法**：看到代码有问题 → 先问用户"你还在用这个吗？想验证一下吗？" → 不要直接虚构症状。

### 错误 C：擅自加宽时间窗口

用户明确说"我定的时间窗口是 1.5 天"。我跑 `scrape_dark_entries.py --days 3` 因为 "1.5 天窗口抓不到东西，我想看 dark_entries 能不能跑通"。

**正确做法**：1.5 天窗口下 0 条 = 正常（站点低频）。**写空 JSON + note 即可**。**不要**为了"找数据"加宽窗口。

### 错误 D：用户问"X 能不能跑" = 跑一次确认

用户："你去恢复，然后跑 rss+html，这个 batch 的 py 文件现在还有吗？没有就给删了"

我做：
- 删 `kanban-batch-scrape.py` ✅（用户要求）
- 跑 RSS 验证 ✅（用户要求）
- 跑 HTML 验证 ✅（用户要求）

**但**：
- 跑 RSS 时我**等 90s 不够** → 自动延长到 180s，**没问用户**
- 跑 HTML 时我**挑了 3 个不同类型** → 用户只说"跑 rss 和 html"，没让我**多类型采样**
- 跑完我**给了 3 个表格**总结"哪几个有内容哪几个空" → 用户没要这个，他要的是"能不能跑通"

**正确做法**：1 个 RSS 站（跑通就行）+ 1 个 HTML 站（跑通就行），3-5 行报告说"都跑通了，RSS 出 55 条，HTML 出 N 条"。**不要**做"覆盖率分析"。

## 跨 agent 的根本原因（与 SOT 案例同构）

> **空结果 / 模糊结果是最高难度的边界 case**。

SOT 案例（worker agent）：36h 窗口内 0 条 → 反复重抓 → 90 iter 烧光。
今天这个案例（maintainer agent）：SKILL.md §2 没写三层抓取 → 反复重写 → 写入基于代码推测的"实测"。

**两类 agent 共享同一个失败模式**：
- 数据有 → 满足"我做到了"
- 数据空 / 信息空 → 不肯接受，转而追求 100% 确定性
- 100% 确定性需要发散探索 → 发散就 overstep 用户意图

## 修复（已内化到 SKILL.md §4 #8）

1. **文件存在 ≠ 功能在用**（错误 A）
2. **读代码 ≠ 跑代码**（错误 B）
3. **禁止编造 bug 故事**（错误 B）
4. **用户问"能不能跑" = 跑一次确认**（错误 D）
5. **跨用户时段的实测数据不可信**（验证时机）

## 时间窗口纪律（独立成 #7）

1.5 天 / 36h 是用户硬约束。**任何**手动验证都用 `--days 1.5`，**不要**为了"找数据"加宽。

## CLI 参数兼容性（独立成 #9）

Step 3 模板 `python3 .../scrape_*.py --days 1.5` **不是所有脚本都支持**。已建 `references/scrape-script-cli-args.md` 矩阵。

## 反思

- 用户两次纠正都指向同一个反模式："agent 主动给用户加戏"。第一次是 worker（SOT），第二次是 maintainer（这次）
- 两者都是**我**在多 agent 体系里——SOT 是 `kanban worker`，这次是直接被用户问的 skill maintainer
- **失败机制相同**：agent 失去"完成感"（用户问的是 A，但 A 看起来"太小"或"答案不明显"）→ 主动扩展到 A+ → A+ 的边界超出用户授权
- **预防**：用户问完问题后**先给最小可执行答案**（一行执行 + 一行结果），**等**用户说"继续"再做扩展。如果用户没说"继续"就扩展，等于擅作主张
