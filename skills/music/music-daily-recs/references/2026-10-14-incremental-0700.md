# 2026-10-14 07:00 增量评分（fix/incremental-0700）

## 背景
旧逻辑：07:00 watchdog 只要发现任何 `*_reviews.json` 比 `processed.json` 新（包括空结果协议写出的 `items:[]`），就对当天**全部**条目重新评分并 push。
实测后果（用户仓库）：
- 10-08：04:00 与 07:00 共同的 88 条里 43 条分数变化，16 条 04:00 已推送的推荐被撤掉
- 10-09：117 条里 70 条变化（最大差 5 分），8 条被撤
- LLM 调用翻倍，07:00 集中请求触发 429（10-10）

## 新逻辑
`bin/daily_pipeline.py:incremental_update()`，仅在 `--if-needed` 且 `on_origin` 且 `processed.json` 存在时触发：

1. 读旧 `processed.json`：`known = meta.scored_keys ∪ 现存 items 的键 − meta.score_error_keys`
2. 重新 merge → 新 `scraped_raw.json`；`new = 键不在 known 的条目`（同批内再去重）
3. `new` 为空 → 恢复旧 `scraped_raw.json`，返回 `noop`（0 LLM / 0 commit / 0 push）
4. 只把 `new` 写入临时 `incremental_raw.json` → `process_reviews.py` → `incremental_processed.json`（两临时文件跑完即删）
5. 增量 `scored_keys` 为空（全部失败）→ 恢复 raw，返回 `all-failed`，报告与 processed 不动
6. 否则：旧 items 原样 + 新增 >2 分条目 → 写 processed.json（更新 `scored_keys` / `score_error_keys` / `total` / `incremental_runs`）→ 重写报告 → commit + push 一次

## 状态契约（processed.json meta 新增字段）
| 字段 | 含义 |
|---|---|
| `scored_keys` | 已成功评分条目的规范化键（含被删 ≤2 分、预过滤 0 分）。冻结，不重评 |
| `score_error_keys` | 评分失败条目键，可被增量重试 |
| `incremental_runs` | 每次增量的 `{at,new,scored,failed,kept}` |
items 中失败条目带 `_score_error: true`（会被 ≤2 清理删除，主要用于区分来源）。

## 规范化规则（`bin/url_norm.py`）
http/https 视为同一（统一为 https）；host 小写；去末尾 `/`；去 `utm_*`、`fbclid`、`gclid`、`dclid`、`msclkid`、`mc_cid`、`mc_eid`、`igshid`、`yclid`、`_hsenc`、`_hsmi`、`ref`、`ref_src`、`spm`；去 fragment；剩余 query 排序。
