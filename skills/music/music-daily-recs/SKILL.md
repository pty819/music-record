83 站。出货全自动、纯脚本，不进 Kanban，不用浏览器。没有 Verifier，没有 Synthesizer。Kanban 那 5 个 Chromium worker 只做探索，不挡住货。

```
北京时间 04:00  cron music-daily-recs (a889d709f680, UTC 0 20 * * *)
         RSS 60 → HTML 14（纯 HTTP，不起浏览器）→ merge → 评分 → 报告 → git push
         末尾 spawn 5 个 Chromium worker（探索层，失败不挡出货）
         末尾 prune_raw_data.py 清 3 天前的原始数据
         agent 随后核对报告落地与 push 是否成功，汇报条数分布

04:00 起数小时内  Boomkat / PoD / Wild City / JazzTokyo / musicircus
         能抓到就写 {site}_reviews.json
         0 条 / CF / 进程死 → 写空 JSON + kanban_complete

补货（本机暂无 cron，需要时手动）  bin/daily_pipeline.py --if-needed
         报告不在 origin/main → 跑全量管道
         报告已在 origin 且尾巴 JSON 后到了 → **增量**：只给新条目评分
           已推送分数冻结；空尾巴 / 无新条目 → 0 次 LLM、不改报告、不 push
           新条目全部评分失败 → 报告原样保留、不 push
         顺手清 music 看板：卡死 complete，其余 archive
```

```bash

```

## 把站接回 RSS 层：改 sites.json，然后重跑全量验证

免浏览器路子的落地就是两个字段：`has_rss=True` + `rss_url`。RSS 层用 `data["sites"]` 里 `has_rss and rss_url` 的条目驱动，所以**接进去之后必须跑一次真实全量抓取，确认新站真的有条目**——不能只看 `sites.json` 里字段对了就算完。

```bash
python3 bin/fast-rss-scrape.py --days 3 -o /tmp/rss.json
# 然后断言：新 site_id 出现在产出里，且字段齐全（album/artist/url/pub_date/body）
```

⚠️ **schema 里没有 `title` 字段。** RSS 条目的标题落在 `album`，艺人落在 `artist`。用 `it['title']` 断言会报空，看起来像抓取失败，其实是字段名不存在。

⚠️ **RSS 层跑一次会轮转 `data/fluid_radio_archive.json`**（`fluid_radio` 走 archive_pick）。调完之后 `git checkout data/fluid_radio_archive.json` 还原，除非你真的要提交这次轮转。

⚠️ **改完 `sites.json` 站点表就过期了**：`python3 bin/gen_skill_site_table.py --write` 重新生成 SKILL.md 里的 GENERATED SITES 块。RSS 50→51 这类计数变化要同时改 frontmatter description 和正文表格里的数字，否则下一任读到的总数就是错的（错总数会让所有基于它的分层结论失效）。

⚠️ **这个文件里的站数会静默变旧。** 本文件的 frontmatter、正文首句、生成块里各写了一份总数，
三处容易不同步——而一个错的总数会让所有基于它的分层结论失效。报告任何分层结论前，先拿真源对一下：

```bash

rss=[s for s in d if s.get('has_rss') and s.get('rss_url')]
```

然后跑 `gen_skill_site_table.py --write` 重新生成，并把 frontmatter description 与正文首句
的数字一并改成一致。**四处数字（frontmatter / 首句 / 生成块 / 表格行）必须对得上。**

判定某个脚本属于哪类，别只看 `import`：

```bash
grep -q "chromium_browser" bin/$S.py && echo "需浏览器"
grep -qE "urllib|requests|http\.client" bin/$S.py && echo "纯 HTTP"
```

```python
from hermes_cli import kanban_db as kb
from hermes_cli import kanban_db_connect as kbc
with kbc.connect_closing() as conn:
    ...
```

`kb.list_tasks` / `kb.create_task` / `kb.complete_task` 仍在 `kanban_db`，只有连接器搬了家。

⚠️ **venv 里没有 `pip` 可执行文件**（`python3 -m pip` 也没有）。装包用 `uv pip install --python .venv/bin/python <pkg>`。系统 python 有 `requests`/`ruamel`，但脚本跑在 venv 里，**系统装了不算数**——路径要用 `.venv/bin/python` 验。

```bash

```

# 浏览器层

**Camoufox 已于 2026-10-18 完全移除。** 曾用 `bin/chromium_browser.py` 驱动 Hermes 自带 Chromium（`~/.hermes/tools/chromium-*/chrome-linux64/chrome`）走 CDP，取代 9377 端口的 Camoufox REST 服务。迁移手法（REST 契约同形替换 `from chromium_browser import LocalApiClient`）仍适用于探索层，但**出货路径现在完全不起浏览器**。

## 出货路径必须无浏览器

本机 1.6GB RAM，Hermes 网关常驻约 545MB。实测单个 Chromium 站会拉起 **~74 个子进程、RSS 冲到 935MB，可用内存掉到 137MB**，内核 OOM killer 静默杀掉 chrome。

失败形态具有欺骗性：**`empty stdout` + 0 条，stderr 无异常，进程消失得干干净净**。看日志只会以为“该站没更新”，不会想到是内存。

已试过且**均无效**，不要再重复：

- 降 V8 heap：`_heap_mb()` 已经到 `max(128, ...)` 下限
- Chromium 站串行化：串行照样被 OOM killer 杀（并发只是让它来得更快）
- 换机器扛（Pi）：另一台机器上 chrome 渲染同样挂死（另一个大内存常驻服务占满）

所以正确做法不是“把内存调好”，而是**把浏览器从出货路径拿掉**。判定标准：`SCRIPTS` 里不应存在任何 `import chromium_browser` 的条目。

```bash
sed -n '/^SCRIPTS = \[/,/^\]/p' bin/scrape_html_parallel.py | grep -c chromium   # 期望 0
```

## 遇到新的 JS 渲染站怎么办

**先查有没有免浏览器的路子，再考虑要不要放弃**。探测流程见 `references/site-investigation-methodology.md` 的「RSS / 服务端渲染探测」。

免浏览器路子的优先级：真 RSS > 服务端渲染 HTML > 浏览器。绝大多数“需要浏览器”的站其实只是没人找过 feed。

Chromium 层本身仍然保留在 `bin/chromium_browser.py`（自检 `python3 bin/chromium_browser.py --self-check`），供探索层和一次性排查用。CDP 本身的坑（握手 403、per-target 域、函数表达式、`atexit` 清理、navigate 复用 target、OOM 与内存上限、后台任务轮询）看 `headless-browser-scraping` skill。

## 仓库里放什么、不放什么

GitHub 上能看到的东西只有两类：**成品**和**能重建它的代码**。中间产物不进版本库。

| 路径 | 进 git？ | 为什么 |
|---|---|---|
| `recommend/YYYY/MM/YYYY-MM-DD.md` | ✅ 永远 | 成品日报，唯一不可再生的东西 |
| `bin/` `skills/` `tests/` | ✅ 永远 | 代码与文档 |
| `data/sites.json` | ✅ 永远 | 83 站配置 |
| `data/fluid_radio_archive.json` | ✅ 永远 | fluid_radio 的 RSS 被博彩 SEO 污染，800 条存档是唯一补货源（已抽 169 条） |
| `2026/**/…_reviews.json` `rss_merged.json` `scraped_raw.json` `processed.json` | ❌ 不进 | 可再生中间态；报告已完整覆盖每一条（报告 `###` 条目数 == `processed.json` items 数，逐日核对一致） |
| 根目录散落文件（`scraped_raw.json`、`screenshot.png`） | ❌ 不进 | debug 遗留，0 处代码引用 |

**raw 不进 git 不只是加一条 `.gitignore` 就完了**——`daily_pipeline.py` 的 `git_push_daily()` 原本显式 `git add -- <date_dir>`，光靠 ignore 挡不住；`prune_raw_data.py` 原本 `git add -A -- 2026` 记录删除动作。改这两个地方时必须同步确认，否则会出现「文件被删 → git 记一条删除 → 第二天又被 add 回来」的死循环。改完用 `grep -rn "git.*add" bin/` 确认没有别的脚本还在 add 那个路径。

⚠️ **`.gitignore` 的目录排除陷阱**：规则是「最后一个匹配者胜出」，但**目录被整体排除后 git 不再下钻该目录**，写在后面的 `!` 例外永远不会生效。想放行目录里的某个文件，必须**按文件类型排除**（`2026/**/*.json`），不能写 `2026/` + `!2026/**/*.md`——后者用 `git check-ignore -v` 实测是「仍被忽略」。`2026/04/2026-04-29.md` 是 v0.9 时代的历史日报，落在 raw 目录里但 `recommend/` 下无副本，靠这条放行保住。

⚠️⚠️ **无锚定的目录规则会连成品目录一起吃掉（2026-10-20 踩中，日报没进仓库）。** 把 raw 目录改成整目录排除时写成了 `2026/`——git 的目录规则不带前导斜杠就匹配**任意层级**的同名目录，于是 `recommend/2026/` 也被排除。

失败形态极具欺骗性：**`git add` 打印 "ignored by one of your .gitignore files" 但退出码仍是 0**，commit 照样成功、push 照样成功、pipeline 照样打印 `pushed=True`——**只有成品日报根本没进仓库**。判据不是 push 成功，而是「报告在 origin/main 的 tree 里」：

```bash
git ls-tree -r --name-only origin/main -- recommend/YYYY/MM/YYYY-MM-DD.md   # 必须有输出
git check-ignore -v recommend/YYYY/MM/YYYY-MM-DD.md                          # 必须无输出
```

修法：**目录规则加前导斜杠锚定到仓库根**——`/2026/` 而不是 `2026/`。raw 目录本来就在仓库根，锚定后行为不变；`recommend/2026/` 不再被误伤。

`daily_pipeline.py:git_push_daily()` 现在会在 `git add` 之后显式跑 `git ls-files --error-unmatch <报告>`，报告没进 index 就直接 `SystemExit` 硬失败——**宁可整条管道报错，也不要安静地 push 一份缺日报的 commit**。

⚠️ **排除目录前先把里面每个文件分类一遍。** raw 目录里可能混着「看起来像中间产物、其实是成品」的文件（那份历史日报就是）。按类型排除而不是按目录排除，也是为了这类文件不被连带。

**新增文件前先问一句**：它是成品，还是能被下一次运行重新生成出来的东西？后者就别提交。

# 改代码后怎么验真

改完抓取/浏览器/评分代码，**测试绿不等于能出货**。按下面顺序验，每一步都有具体的“它到底证明什么”：

1. `python3 -m pytest tests/` 全绿 — 只证明纯逻辑没坏。**改过 `messages.create()` 入参后，假 SDK `tests/fakeanth/` 的签名要同步**，否则每个用例以 TypeError 失败、日志为空、断言拿到 0 次调用（见“评分 provider”）。
2. `python3 bin/chromium_browser.py --self-check` — 证明浏览器层能独立跑。
3. 单站实跑，看**条数**而不只是 exit=0 — 条数 0 或全量都是导航标签（`/music/reviews` 这种栏目名）都是坏信号，不是好结果。
4. 抓 25 篇这种长任务，**完成后统计正文非空的条数**。`0 bytes` 输出 + stderr 无报错 = 被 OOM 静默杀了，`dmesg -T | grep "Killed process"` 是唯一现场。
5. 后台跑时用 `pgrep -f 'scrape_<name>'` 判存活，**不要轮询 `nohup ... &` 打印的 pid**——那是 shell wrapper，退了不代表任务完，轮询它会反复误报“已结束”。

反过来，**改文档/注释时必须跟代码同步**：`grep -rn "9377" bin/` 会有命中在 docstring 和迁移说明里，这些是故意保留的“原来是什么”记录，不是漏网。只看命中数量会误判“还没改完”，得看每条命中的上下文。

# 少问、多做

用户已经明说「我不管那些，反正你保证每天的音乐推荐照常拉然后 push 到 GitHub」——**运维决策权在你手上，不是他的**。

## 判据：问之前先回答「他的答案会改变我要跑的命令吗？」

会 → 问。不会 → 别问，做完一句话汇报。

本会话里反复踩的坑是**拿 A/B/C 选项去问一个根本不需要授权的技术选型**。用户已经被同一件事问烦了：

- 「保证每天照常拉就行」之后，你又问「加 swap 还是砍站还是上 Pi」
- 用户已经说了「别搞了」「你直接跳过吧」，你还是反悔回去做 Pi 方案
- 每轮结尾都抛「要我动手吗 / 你倾向哪个」，把「你保证」又变成了「你选」

**触发词一出现就已经是决定了**：别搞了 / 算了 / 你直接 X / 不用问 / 我不管 / 随便。按字面执行，不要一边执行一边保留备选方案问你意见。

## 该自己拍板的

- **保留策略、站点取舍、内存参数、调度时刻**：直接选一个可行方案做掉，事后一句话说清。
- **可回滚的代码改动**（改 SCRIPTS、删站点、注释掉脚本）：直接做。删东西就 comment-out 而不是真删，并说清怎么恢复。
- **环境探测**：跑一个 5 秒的 HTTP 请求来回答「这个站有没有 RSS」，比问「要不要我查一下」强得多。
- **加 cron、改调度时刻**：用户说了具体时间就直接建。建完把时区换算算给他看，不要反问确认。

## 必须先问的

- **不可逆且影响生产**：改系统分区、加 swap、删用户数据、重写 git 历史、动 Pi 上用户密码保护的配置。
- **会静默消耗用户资源**：对外大流量、长时间挖矿式重试。

## 一条边界：**你为了清场而做的事，也要授权**

本会话的真实教训：用用户给的密码往 Pi 上装了公钥，之后想「顺手撤掉保持干净」，命令超时被拦——而拦是对的。**我加的不等于我能删**。装公钥是用户授权的，撤公钥是另一个决定，同样要他点头。

清理自己的临时文件不需要问（那是 hygiene 规则）；**动别人机器上的持久配置需要问**。

## 撞到授权拦截就停

命令被拦（`BLOCKED… the user did NOT consent` / `timed out without user response`）时：**当场停止，不换写法重试，不绕道达成同一结果**。把它当作用户拒答，并在回复里说清「这一步没做、等你一句话」。

有个真实教训：为了让 cron 跑干净想去删 Pi 上的公钥，命令超时被拦。正确做法是停下来告知，而不是改成 grep/mv/ssh-copy-id 变体重试——**换工具达成同一个未授权结果，一样是越权**。

同理，拿到密码（`liyifan/liyifan`）安装公钥后，**撤除它也需要用户点头**。临时凭据一旦用完就报告清楚现状，不要因为「我加的所以我能删」。

## 降级要明说，不要静默

内存不够而砍掉 3 个站时，必须在汇报里写清楚「哪些站没了、为什么、能不能恢复」。静默降级比报错更糟——用户会以为日报还是完整的。

# 报进度时报范围，不要报印象

“搞定了”必须落到**具体的数**，否则用户会替你查。反复问“是不是所有都搞定了”的信号是：上一条回答只说了总量而没分层。

按下面三层报，一层一句话 + 一个数：

| 层 | 范围 | 坏了的后果 |
|---|---|---|
| 出货层 | `SCRIPTS` 的 14 站 | 日报停产 |
| 探索层 | 5 个 Chromium worker | 只少探索，日报无感 |
| 旁支 | `_debug_*` / `retry_*` 等一次性脚本 | 无 |

⚠️ 「日报照常拉」不等于「和以前一样全」。被跳过的站要在汇报里点名，否则用户以为 74 站都在跑。

已经踩过两次的坑：

- **不要把“改了站点表的分类标签”说成“改了脚本”。** 两者是两件事；前者只改文档，后者才改代码。用户问“所有网址都处理好了吗”时，指的是后者。
- **不要把未验证的推断说成实测。** 声称某个 fallback “调了必坏”之前，先确认那个分支真的在出货路径上——本例中 `downbeat` 的 9377 fallback 失败时返回 `None`，不会硬失败，而探索层脚本根本无人调用。“坏了”有很多种含义，出货层与非出货层的含义完全不同。
- **发现误判要主动更正，不要等用户问。** 报错范围时先自己核一遍，出货/探索层要分开给数；发现自己上一条说大了，就在下一条开头直接说“我之前说 X 夸大了”，再给准确范围。

分层的另一个用途：用户说“把没用的删了”时，先按上表归类再动手。删除只对**旁支**成立；探索层脚本虽然零引用，但对应站点仍在名单上，属于“待修”而不是“废弃”，静默删掉等于把可见的报错换成静默的能力缺失。

## 零引用不等于废弃

用户说「把没用的删了」时，先分层再动手。删除只对**旁支**（`_debug_*`、`retry_*` 等一次性脚本）成立。

**误删过的真实例子**：`gen_skill_site_table.py` 在代码里零引用，grep 判定「无人调用」——但 SKILL.md 写着它是站点表的再生命令，改完 `sites.json` 必跑。**代码引用只是用法之一，文档引用同样算数。** 删之前把 `SKILL.md` + `references/` 一起扫一遍。

探索层脚本虽然零引用，但站点仍在名单上，属于「待修」不是「废弃」，静默删掉等于把可见报错换成静默的能力缺失。

## 「报告只有 0 条 / 只有百来字节」先查 cron 还在不在跑

用户看到日报空了第一反应是「内容太少」「站是不是白加了」。**报告文件是流水线的中间产物，评分阶段跑之前它本来就是空的**——先证明任务结束了，再谈产出。

```bash
# 1. 任务状态（SQLite 在 cron 目录里）
python3 -c "
import sqlite3
db=sqlite3.connect('/root/.hermes/cron/executions.db'); db.row_factory=sqlite3.Row
r=db.execute('SELECT status,started_at,finished_at,progress_at,error FROM executions ORDER BY rowid DESC LIMIT 1').fetchone()
print(dict(r))"
#   status=running → 还没跑完，此刻报告为空是正常的，别报故障
#   status=failed  → 看 error 字段

# 2. raw 目录里已经有数据 = 抓取阶段过了
ls -lh 2026/10/$(date -u +%F)/     # rss_merged.json / scraped_raw.json 有体积 = 抓到了
```

⚠️ **只看报告文件会得到完全相反的结论。** 实测：20:04 的报告只有 169 字节写着「共整理 0 条乐评」，看起来像管道崩了；实际上 cron 20:00 启动、20:05 仍在 `running`，raw 目录里已经躺着 346K 的 `rss_merged.json`。用户拿这个空报告质疑站点数量，而真因是文件还没写完。

⚠️ **第二种「0 条」：抓到了，但评分阶段整批失败。** 抓取成功、评分全灭时，报告同样写「共整理 0 条乐评」——用户看到的和「没抓到」一模一样，但真因完全不同（provider 被拒，不是站点问题）。靠 `processed.json` 区分：

```bash
.venv/bin/python -c "
import json
d=json.load(open('2026/10/$(date -u +%F)/processed.json'))
items=d.get('items',[])
print('抓到:',len(items))
print('有分数:',sum(1 for i in items if i.get('score') not in (None,0)))
print('评分失败标记:',sum(1 for i in items if i.get('_score_error')))
"
```

抓到 > 0 而「有分数」= 0 → 是 provider 被拒（MiniMax Token Plan 配额耗尽 429），
报告里的 0 条是**评分**的空，不是**抓取**的空。MiniMax 429 是持续性配额耗尽、
不是瞬时限流，恢复要等配额窗口；这也是配 GLM-5.3-Flash 兜底的理由——主 provider
429 时自动切过去，报告不该再出现「抓到 N 条但 0 评分」。

⚠️ 同理，**「某站没出货」不等于「那个站白加了」**。区分三件事：管道没跑完 / 站真的没更新（先跑 `references/site-investigation-methodology.md` 的 1b 节放宽 `--days`）/ 站还在但落在时间窗外（月更站在 `--days 1.5` 里必然 0 条）。

## 问「昨天哪些站爬失败」——先分清三态，再回答

「爬失败」「零产出」「当日未更新」是三件不同的事，报成一件就是误报。回答前先把每站归类：

| 状态 | 判据 | 怎么发现 |
|---|---|---|
| **抓取失败** | 有 HTTP 错误码 / CF 挑战 / 超时 / 解析异常 | 抓取阶段的错误日志里点名了站点 |
| **抓到了但零产出** | 请求 200、解析成功，条目数 0 | 该站在成功列表里但计数为 0 |
| **当日未更新** | 管道根本没跑到该站，或报告没落地 | 该站既不在成功列表也不在失败列表 |

**证据只可能在 cron 输出日志里，不要去翻原始数据目录。** 原始数据只留 3 天（`bin/prune_raw_data.py`），而 cron 输出永久保留：

```bash
ls -t ~/.hermes/cron/output/a889d709f680/*.md | head -3
# 读最近一次的「## Response」段，里面逐站列了成功/失败/条数
```

任务结束后先看 `## Response` 段再下结论。**日志里写「0 error」不等于「每个站都有产出」**——HTML 层 14 个脚本全部无报错，同时可能有 11 个站正常抓取但零产出（站点停更或月更），这与「零个站失败」是两回事。**把两者都报出来：失败名单（带状态码/原因）+ 零产出名单（无错误、但没货）**。

⚠️ **静默失败的站不会出现在错误列表里。** 反爬挑战页会返回 HTTP 200，feedparser 解析出 0 条且不报错——在日志里它表现为「成功但 0 条」。判断「零产出」是不是反爬，看该站是否有反爬指纹：返回 200 但条目数为 0、同时站点带反爬服务商（WAF / bot defense）特征。处理方式是**降级 TLS 指纹**（不带 ALPN/PHA 的 `ssl.create_default_context()`），不是加超时。参考 `references/2026-10-23-fastly-client-challenge.md`。

# 仓库里的 skill 副本 ≠ 安装的 skill

`/home/liyifan/music-record/skills/music/music-daily-recs/SKILL.md`（仓库内）和
`~/.hermes/skills/music/music-daily-recs/SKILL.md`（**实际被加载的那份**）是两个不同的文件，
内容会分叉——仓库那份可能是旧的精简版，装好的那份累积了更多结论。

**下一任 session 加载的是安装版。只改仓库那份 = 改动根本没被加载。**

```bash
diff <repo>/skills/music/music-daily-recs/SKILL.md \
     ~/.hermes/skills/music/music-daily-recs/SKILL.md | head -40
```

`scripts/` 同理：安装版的 `scripts/` 是仓库 `bin/` 的副本，逐文件比对：

```bash
for f in <repo>/bin/*.py; do
  b=$(basename $f)
  diff -q "$f" ~/.hermes/skills/music/music-daily-recs/scripts/$b >/dev/null 2>&1 \
    || echo "不一致: $b"
done
```

改完仓库代码要把安装版同步过去（`cp` 即可），否则「仓库已改」不等于「生产已改」。

**两处都要对**：生产 cron 跑的是**仓库**里的 `bin/`（prompt 里 `cd /home/liyifan/music-record`），
而 skill 文档描述的是**安装版**——只改一边会留下「文档说 A、代码跑 B」的裂缝。

### 同步方向按内容类型定，**references 走并集而非单向**

| 内容 | 母版 | 流向 |
|---|---|---|
| `SKILL.md` 正文 | **安装版** | 安装版 → 仓库 |
| `references/*.md` | **并集** | 双向：仓库独有的历史 reference 补回安装版，安装版独有的补进仓库 |
| 代码（`bin/*.py`） | **仓库** | 仓库 → 安装版 |

理由：文档是结论的累积地，下一任 session 加载的是安装版；代码是生产本体，cron 跑的是仓库那份。

**方向搞反的代价是静默的**：文档反了 = 改动没被加载；代码反了 = 仓库里的改动被安装版覆盖回去。
所以改代码只改仓库、改文档只改装版，然后交给同步机制。

⚠️ **references 走单向会造出断链。** 只做「安装版 → 仓库」时，仓库里独有的历史 reference 永远不会进安装版——而 `SKILL.md` 正文可能已经引用了它（实测：`SKILL.md` 引用了 `2026-10-14-incremental-0700.md`，该文件只在仓库树里存在，安装树断链）。**同步的是文件集合，不只是两边都有的那几个文件。**

⚠️ **同步后必须验引用完整性，不能只看两边逐字节一致。** 一致 ≠ 完整：两边同步了同样的 23 个文件、正文也一致，但正文引用的某个 reference 若两边都没有，断链照样存在。判据是「正文引用的每个 reference 在本树都存在」。

### 同步已自动化，不要靠「记得 cp」

手工同步会漏。实测漂移规模：安装版 `SKILL.md` 累积到 37KB / 41 章节，仓库副本还停在
10.8KB / 13 章节，**仓库从未收到过那些章节**；安装版 `scripts/` 也落后 4 个文件，
其中 `prune_raw_data.py` 整个缺失。

`bin/sync_skill_to_repo.py` + cron `skill-sync-to-github`（job `d129e61e3cc1`，`every 120m`，
`no_agent`）负责：检测漂移 → 按母版方向同步 → git add/commit/push → 打印
`SKILL_SYNCED: N changed -> pushed <hash>`。**无变化时 stdout 为空**，不投递、不制造噪音。

详细流程、母版规则、验证方法（造真实漂移走完整链路，而不是只看脚本不报错）见
`references/skill-repo-sync.md`。
