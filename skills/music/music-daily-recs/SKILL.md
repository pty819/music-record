# Kanban Swarm 内部

## Camoufox Workers（5 个）

由 kanban-swarm.py 自动创建。每个 worker 的 body 包含站点 URL、`--days 1.5` 约束、~90 iteration budget（Kanban dispatcher 默认，configurable）。worker 完成后输出 `_reviews.json`。

## Verifier

body 步骤（`VERIFIER_BODY` in kanban-swarm.py）：
1. `merge_scraped.py` 合并 RSS + HTML + Camoufox 数据 → `scraped_raw.json`
2. 验证 `items > 0` 且含 `site_id` 字段
3. 通过 → `kanban_complete(metadata={gate: pass, total_items: N})`
4. 失败 → `kanban_block(reason=...)`

## Synthesizer

body 步骤（`SYNTHESIZER_BODY` in kanban-swarm.py）：
1. `process_reviews.py --max-workers 3` → `processed.json`
   （前置过滤商品页/博彩污染 + LLM 评分 + 中文总结 + **物理删除 <=2 分条目**）
2. `generate_report.py` → `recommend/YYYY/MM/{DATE}.md`
   （默认 `--min-score 3`，只显示 >=3 分；报告不含 "📋 参考(1-2)" tier）
3. **上库前清理检查**：确认 processed.json 无 <=2 分条目 + recommend/YYYY/MM/{DATE}.md 无 <=2 分
   ```bash
   python3 -c "
   import json
   p = json.load(open('2026/\$(date +%m)/\$(date +%Y-%m-%d)/processed.json'))
   low = [i for i in p['items'] if i.get('total_score', 0) <= 2]
   print(f'processed.json 剩余 {len(p[\"items\"])} 条, <=2分: {len(low)} 条', '✅' if not low else '⚠️ 有残留!')
   "
   ```
   ⚠️ 若检测到 <=2 分残留，先手动删除再继续（`sed -i` 或重新跑 process_reviews.py）。
4. `git push origin main`（此时已确保低分条目不随代码/数据上库）
5. Telegram 推送（≤4000 字符全文，否则精简 + GitHub 链接）
6. `hermes kanban list --tenant music --status done | awk '{print $2}' | xargs hermes kanban archive` 归档本轮已完成任务（仅 music tenant）
7. `kanban_complete`

### 评分质量门（Step 1.5）

Synthesizer Step 1 后跑一个 Python 检查，**不阻塞**但生成告警：
- 读取 `processed.json` 的 `meta.filtered/failed/failed_items/filter_breakdown`
- 告警条件：
  - `failed/total > 10%` → "评分失败率 X% 超阈值（MiniMax API 或数据问题）"
  - `filtered/total > 30%` → "内容过滤率 X% 超阈值（可能上游抓取配置异常）"
  - 失败明细列出前 5 条 album+site+reason
- 当前已知过滤类别：
  - `product_page`：boomkat 商品页（三重命中 "MP3 Release" + £价格 + "Add to crate"）
  - `spam_fluid_radio`：fluid_radio 博彩 SEO（已被 archive_pick 模式绕过，但规则保留作为兜底）
  - `spam_generic`：通用赌博推广关键词

### 低分清理（2026-08-15 新增）

- `process_reviews.py` 写完 processed.json 前，**物理删除 <=2 分条目**（`LOW_SCORE_CUTOFF = 2`）
- `generate_report.py` 默认 `--min-score 3`，且已删 "📋 参考(1-2)" tier → 报告只含 3-10 分
- 目的：省磁盘 + 报告干净（用户要求"2分及以下都是没用的东西，占我空间"）
- 被删条目：过滤（0分）、评分失败（0分）、低分乐评（1-2分）
- 若需临时保留低分数据做分析，用 `--min-score 1` 覆盖 generate_report 即可，但 processed.json 已物理删除无法恢复（上游 scraped_raw.json 仍在）

# 评分（v4 — 多 Provider 容错）

`process_reviews.py` 用 **多 provider 容错层**（`bin/provider_failover.py`）评分，主 MiniMax-M3 + 备火山 Ark DeepSeek-v4-flash。评分+中文总结同一次 API 调用，线程池 3 并发。

**为什么加 failover**：MiniMax CN Token Plan（`sk-cp-` 前缀）在凌晨时段偶发配额耗尽（429 错误 2056「用量上限」），曾导致 2026-08-16 评分全挂、推荐中断。加备通道后，主 provider 429/持续失败 → 自动切 Ark，每日推荐不中断。

**provider 定义**（`provider_failover.py:PROVIDERS`）：
| # | 名称 | 端点 | 模型 | key 来源 |
|---|---|---|---|---|
| 0 | MiniMax（主） | api.minimaxi.com/anthropic | MiniMax-M3 | `~/.config/music-recs/minimax_cn_key` 或 `MINIMAX_CN_API_KEY` |
| 1 | Ark（备） | ark.cn-beijing.volces.com/api/coding/v1 | deepseek-v4-flash-ga-260731 | `HERMES_CUSTOM_ARK_CN_BEIJING_VOLCES_COM_API_KEY` |

**容错逻辑**：
- 单条失败重试 2 次（指数退避）→ 仍失败切下一个 provider
- 配额/429 类错误（2056/用量上限/quota/rate limit）→ 立即切，不重试
- 所有 provider 都失败 → 该条记 `fail`（0 分，后续清理）
- 切换记录写进 `processed.json` 的 `meta.provider_stats` / `meta.provider_switch_log`，报告可追溯

**验证**：`python3 bin/provider_failover.py --self-check`（两 provider 连通性探测）。

> 迁移记录：`references/2026-06-15-api-provider-migration.md`（从 Tencent Cloud hy3 迁移到 MiniMax M3）。
> 2026-08-16 新增：`references/2026-08-16-provider-failover.md`（多 provider 容错，解决 MiniMax 凌晨配额单点故障）。

# 恢复

| 症状 | 处理 |
|---|---|
| cron 未触发 | `hermes cron status`；`journalctl --user -u hermes-gateway` |
| gateway stopped | `hermes gateway run --replace` |
| worker 卡 ready | `hermes kanban dispatch` |
| worker running 但无进程 | `hermes kanban complete <id>` |
| verifier gate=block | `hermes kanban show <verifier_id>` 看日志；手动重跑 merge 后 `hermes kanban edit <verifier_id> --add-metadata '{"gate":"pass"}'` |

# Pitfalls

| 症状 | 原因 | 处理 |
|---|---|---|
| **scrape 脚本不认 --days** | parallel scraper 统一传 `--days 1.5`，但有些脚本只认 `--hours` 或 `--ref-date` → rc=2 | 脚本必须加 `--days` 支持。新脚本上线前 `--help` 验证 |
| **stdout 模式脚本不输出到 stdout** | 脚本只 `json.dump(f)` 写文件不 `print()` → parallel scraper 捕获 0B | stdout 模式必须有 `print(json.dumps(result))` |
| **`html_reviews.json` 写入 CWD 而非 `--out-dir`（已修复）** | 旧版 `scrape_html_parallel.py` 将合并后的 `html_reviews.json` 写到 CWD（`./html_reviews.json`），而非 `--out-dir` → merge 可能找不到 HTML 数据。**当前版本已修复，直接写入 `--out-dir`。** | Step 3 后仍建议检查 `$DATE_DIR/html_reviews.json` 是否存在。若不存在，复制 `./html_reviews.json` → `$DATE_DIR/`：`[ -f ./html_reviews.json ] && [ ! -f \"$DATE_DIR/html_reviews.json\" ] && cp ./html_reviews.json \"$DATE_DIR/html_reviews.json\"` |
| **`$DATE_DIR` 跨 terminal 调用丢失** | cron 各步骤用独立 `terminal()` 调用时，前一步设的 `$DATE_DIR` shell 变量在后续调用中不可见 → merge 等命令指向错误路径或写错目录 | 所有用到 `$DATE_DIR` 的命令必须用绝对路径硬编码，或在每个需要的 terminal 调用中重复声明 `DATE_DIR=...`。推荐方式：`DATE_DIR="/home/liyifan/music-record/2026/$(date +%m)/$(date +%Y-%m-%d)"` 在每个需要它的 terminal 调用中重复声明，或用 `&&` 串联 |
| **wild_city 归类错误** | 脚本调 `CAMOFOX_BASE` REST API 但被放进 HTML_SCRIPT_IDS | 新站上线前 `grep CAMOFOX_BASE` 确认依赖 |
| **Cron 用旧版 skill** | commit 在 cron 之后 → git pull 拉不到新代码 | 改完立即 `git push`；重大改动手动 `hermes cron run` 验证 |
| **RSS 全部 0 条** | VPN TLS 握手超时（15s 太紧） | `socket.setdefaulttimeout(30)` + terminal timeout=900 |
| **HTML 全部 0B + VPN 断连** | Meta VPN 断连时 bandcamp 返回 000（不是 200）。注意：即使 VPN 正常，个别 HTML 站（all_about_jazz, musique_machine, truth_and_lies_music, mixmag_asia）仍可能返回 HTTP 500，这是站点服务端问题，不是 VPN 问题。merger 容忍单脚本失败，继续执行即可 | `curl -s -o /dev/null -w "%{http_code}" https://daily.bandcamp.com/feed` 检查；000 = VPN 断连，200 = VPN 正常。RSS 在 VPN 断连时可能仍可工作（部分站不依赖 VPN） |
| **git pull 失败，GitHub DNS→28.0.0.x** | Meta VPN 选择性 DNS 投毒：github.com/bandcamp 解析到 28.0.0.x 且 TLS 握手失败，但其他站（quietus, pitchfork）正常 | 跳过 Step 1，直接继续 Step 2-5。代码已在磁盘上，git pull 非阻塞。网络恢复后 synthesizer 的 `git push` 仍可能失败 → 见恢复表 |
| **部分站 HTTP 500，部分正常（VPN 正常时）** | 站点自身服务端问题（Cloudflare、反爬、临时故障），不是 VPN 问题。今日实测：bandcamp=200 但 all_about_jazz/mixmag_asia/truth_and_lies_music/musique_machine 仍返回 500 | `scrape_html_parallel.py` 容忍单脚本失败，merger 仍可产出。继续执行，不要等网络恢复。如连续多日同站 500，考虑升级到 Camoufox 层或加反爬头 |
| **HTML 站 403 Forbidden** | all_about_jazz（Cloudflare 预期行为）、musique_machine、mixmag_asia 在特定 VPN 路由下返回 403。**truth_and_lies_music 已于 2026-08-16 迁到 RSS（Squarespace /magazine?format=rss），不再走 HTML 层** | merger 容忍单脚本失败。继续执行，不重试。如连续多日同一站 403，考虑升级到 Camoufox 层或加反爬头 |
